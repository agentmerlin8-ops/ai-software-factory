# Factory Kit v0.1 — Context Bundle Grill (adversarial review, 2026-09-28)

Bundle reviewed: `kit-v0.1/prd.md`, `kit-v0.1/architecture.md`, `kit-v0.1/test-strategy.md`, `kit-v0.1/target-repo-readiness.md`.
Context skimmed: `docs/context-bundle.md` (conventions template), `onboarding/README.md`, `onboarding/onboard.sh` (current implementation).
Constraint per dispatch: the private reference implementation is NOT accessible to builder agents; these docs must be self-contained.

## Verdict — REVISIONS REQUIRED

Two classes of defects block decomposition. First, a hard architectural contradiction: the ledger's claim/handover "push-on-write, first-push-wins" discipline (PRD FR-6, architecture Integrations) cannot coexist with mandatory main-branch protection / no-direct-push (readiness C-3) — the docs never say which branch the ledger lives on or how ledger-only commits reach it, and this is the exact machinery the handover drill (D-2) must prove. Second, the bundle is not self-contained: the controller's per-transition evidence catalog, the role catalog, the gate implementations, and the ledger schema per event type are all specified only as "ported from the private reference implementation" — which builders cannot read, so they would have to invent the heart of the state machine. Most fixes are localized doc edits plus one real architecture decision (ledger push model), but the volume of invented-decision surface is too high to approve as-is.

## Critical issues (block the factory run)

1. **[architecture + prd + readiness] Ledger branch & push model contradicts branch protection — the core race machinery is undefined.**
   PRD FR-6: "Claims and handovers push on write; races are resolved first-push-wins." Architecture Integrations: "push-per-gate … claims/handovers push-on-write; preflight fetch + staleness check." Readiness C-3: "Main branch protected (no direct pushes; PR required)." `factory/ledger/events.jsonl` is a single shared append-only file, but no doc says which branch it lives on. If it lives on main, push-on-write is impossible under C-3. If it lives on story branches, cross-machine first-push-wins and the D-2 fresh-clone resume cannot see claims. Additionally, two machines appending to the same JSONL produce a merge conflict (same file, same region); "exactly one claim exists in the ledger" (FR-6 scenario 3) has no defined mechanism — git merge of concurrent appends can preserve *both* lines.
   **Why it breaks:** FR-6, D-2 (all four variants), and the entire pickup-developer persona (P3) are unimplementable without this decision; a builder would invent a push/merge protocol that likely fails the drill.
   **Fix:** Freeze in architecture §Integrations: (a) ledger lives on `main`; (b) branch protection permits ledger-only direct pushes by operators (or names the exemption mechanism — e.g., a `factory/*` bypass actor, or ledger pushes go through an auto-merged PR — pick one); (c) claim write protocol = fetch → append → push with retry-on-non-fast-forward, and on rebase the appender **re-validates claim uniqueness before pushing** so a duplicate claim event never lands; (d) define conflict resolution for events.jsonl (append-only line-union rebase, then controller adjudication via `correction` event if a duplicate slipped through).

2. **[all four docs] Bundle is not self-contained: the state machine's evidence catalog, role catalog, and per-type ledger schemas exist only in the inaccessible reference implementation.**
   Architecture: "Every arrow = a controller transition with evidence + checks" — but the evidence key required for each of the ~16 transitions is never enumerated. Architecture event types list 13 types — required fields are given only for `assignment`/`handover`; `transition`, `dispatch`, `usage`, `stage`, `finding`, `loop`, `correction`, `recovery`, `outcome`, `human_gate`, `override_used` have no schema. The "Ported from" column repeatedly says "private reference implementation, genericized"; PRD Out-of-Scope cites "reference-spec §7"; architecture open items reference gate identifiers "G12/G13/G14" that appear nowhere in the bundle. The **role catalog** (which roles exist: planner? coder? reviewer? fixer? …) is never listed, yet dispatch packages, routing matrix, and parity tests all depend on it. Ledger schema tests (test-strategy §2: "Every event type: required fields enforced") cannot be written without the per-type field tables.
   **Why it breaks:** This is the largest invention surface in the bundle — a decomposer would have to guess the evidence contract for every transition, every event schema, and the full role list. Different stories would guess differently.
   **Fix:** Add to architecture: (a) a transition table: from-state → to-state → required evidence keys → gate(s) run; (b) a per-event-type required-fields table (including which fields allow null+reason); (c) a role catalog with one-line role definitions and the role→tier matrix; (d) resolve the G12/G13/G14 naming question inline (see Decisions). Extraction from the reference is a drafting task for the doc author, not a build task.

3. **[architecture vs prd NFR-1] `factory/config.yaml` requires a YAML parser; python3 stdlib has none.**
   Architecture §Configuration: "Target repo config (`factory/config.yaml` or equivalent, v0.1 draft)". NFR-1/test-strategy: stdlib only, "no test dependencies". PyYAML is not stdlib. `tomllib` is stdlib but read-only and requires Python ≥ 3.11 — and no doc pins a minimum python3 version (macOS ships older pythons; NFR-3 claims macOS).
   **Why it breaks:** Either the config format violates the stdlib constraint or a builder hand-rolls a YAML subset parser (unreviewed invention). C-10 ("Config file present + parsed by verify") is also unimplementable as written.
   **Fix:** Pick JSON or TOML (recommend TOML via `tomllib`, pinning Python ≥ 3.11 in Dependencies; fallback JSON), and freeze the config key schema (it is already load-bearing for `sync_board.py` project id, identity, adapter registry, repo path, default branch).

4. **[prd FR-1 vs architecture diagram vs readiness C-7 vs test-strategy commands] Kit/target repo layout disagrees across all four docs.**
   PRD FR-1: kit ships top-level `agents/`, `process/`, `tools/`, `adapters/`, `runbook.md`, `onboarding/`. Architecture target-repo diagram: `factory/tools/`, `factory/gates/`, `factory/ledger/`, `factory/templates/`, `factory/locks/` plus top-level `process/`, `agents/`, `adapters/`, `stories/`, `runbook.md`. Readiness C-7: "Kit installed under `factory/` (runbook, tools, gates, templates, ledger seed)" with verify method "`factory/runbook.md` present; `tools/` executable" — self-inconsistent within one row, and contradicts the diagram's top-level `runbook.md`. Test-strategy commands use `factory/tools` and `factory/gates/`. Current `onboard.sh` installs `factory/runbook.md` and `factory/gates/pre_review_gate.py`. So runbook.md has three candidate locations and tools/ has two.
   **Why it breaks:** Every story that installs, invokes, or verifies a path bakes in a different guess; C-7/C-8 conformance fixtures can't be written.
   **Fix:** Add one canonical target-repo layout table to architecture (kit-repo layout vs installed-target layout, explicitly marked), and state where `process/`, `agents/`, `adapters/` land in the target (C-7's enumeration omits them). Align PRD FR-1, C-7, and test-strategy commands to it.

5. **[prd FR-8 + architecture §Adapter interface] The adapter interface is prose-only, so FR-8's "interface constraint test" and FR-9's model resolution have nothing mechanical to test or execute.**
   Architecture defines an adapter as `README.md` + `models.md` + a "usage" description — all markdown. FR-8 acceptance: "a new adapter … can be added without changing control-plane code (interface constraint test)". A test cannot assert a prose contract; and `model_router.py`'s "per-adapter model table" either parses free-form markdown (fragile, unspecified) or doesn't resolve models at all — yet FR-9 requires the ledger to record "the adapter-resolved model". Readiness A-2 says "model routing table installed (`adapters/hermes/models`)" — a directory, vs architecture's `models.md` — a file (name mismatch).
   **Why it breaks:** The runtime-neutrality promise (G3) rests on this interface; as written, the hermes adapter's "per-role model applied at spawn" and usage harvesting have no callable contract, and the FR-8 acceptance test is unwritable.
   **Fix:** Define a machine-readable adapter manifest (e.g. `adapters/<name>/adapter.json`: name, prerequisites checks, tier→model table, usage-report command, identity convention). FR-8's test then validates manifest schema + presence; `model_router` reads the manifest. Fix A-2's path to match.

6. **[architecture vs test-strategy §5 + prd FR-3] Dispatch parity (the runtime-agnostic promise) has no real verification path in v0.1.**
   Test-strategy §5 tests parity by feeding the package to "the `human` adapter path (scripted: artifacts committed by a stub executor)" and "the `hermes` adapter path (stub dispatch)". With stubs on both sides, identical paths are guaranteed by the test's own fixtures — the test is tautological and proves nothing about the adapters. The only live execution, drill D-1, runs the **human adapter only** ("human adapter driving"). PRD FR-3 scenario 2 ("executed by the human adapter … and by the hermes adapter … parity check") and the success criterion "dispatch parity between human and hermes adapters on the dress-rehearsal story" therefore have no defined execution: parity with a live model is never actually observed, and "same contract shape" for free-form artifacts (a plan.md?) is undefined.
   **Fix:** Either (a) add a hermes-driven leg to D-1 (one story dispatched through both adapters, artifacts diffed by path/shape contract), or (b) downgrade FR-3 scenario 2 to the mechanical contract test and say explicitly that live parity is deferred; and define "contract shape" concretely (required file paths + required markdown sections/front-matter keys per role output).

## Important issues (should fix before build)

7. **[architecture vs prd] State count: "16-state story machine" (FR-5) vs 16 named states **plus** BLOCKED (architecture §State machine).** The diagram lists BACKLOG…CLOSED (16) and "(any) → BLOCKED → resumes at originating state" — that is 17 states. Also undefined: how "originating state" is recorded/resumed (via `recovery` event?), whether claims survive BLOCKED, and whether loop-cap escalation lands in BLOCKED. **Fix:** restate as "16 pipeline states + BLOCKED (17 total)" and add BLOCKED entry/exit evidence rules to the transition table (finding 2).

8. **[architecture vs prd FR-10] `metrics_report.py` reconciles "vs frozen baseline" — no baseline can exist for a freshly onboarded repo, and PRD FR-10 never mentions a baseline.** A v0.1 target has no history to freeze. **Fix:** drop "vs frozen baseline" from v0.1 scope or define baseline as optional (null+reason when absent). Same tool's "unrouted-dispatch census" needs a one-line definition (it maps to FR-9's "any unrouted role = process defect, counted" — say so).

9. **[readiness C-2/C-3 vs reality] gh scope list is wrong/insufficient for what verify must do.** C-2 lists fine-grained-style repo permissions (Contents/Issues/PRs/Metadata "+ Projects for board sync"), but: (a) Projects v2 GraphQL is **not** a fine-grained repo permission — it needs a classic token `project` scope (or org-level auth); the current `onboarding/README.md` PAT list also omits it; (b) reading branch protection (C-3's verify method) requires `Administration: read`, not listed; (c) "API probe call" is unspecified (which probe, against what). The onboarding README (existing convention) and C-2 disagree. **Fix:** freeze one scope table covering board sync + protection reads, and name the exact probe commands per check in the verify registry.

10. **[prd FR-7 + architecture §Override] Override "committed" semantics and placeholder detection are undefined.** "Present + valid + committed" — committed to which ref, and does the check read the working tree, HEAD, or origin/main? A committed OVERRIDE plus an *uncommitted deletion* is ambiguous under "delete to restore". "Placeholder-filled is NOT an override" — no rule defines what a placeholder is (`<...>`? `TODO`? empty?). D-2(d) "delete→relock verified" depends on both answers. The "blob SHA at use time" implies reading the git object, which conflicts with a working-tree read. **Fix:** specify: the override is read as the blob at `HEAD` of the current branch (working-tree file must match HEAD, else fail-closed "uncommitted"), and enumerate invalid-placeholder patterns exactly (angle-bracket template values, empty, literal `TODO`/`CHANGEME`).

11. **[architecture §Data model] `override_used` is listed as an event type **and** as "annotation payload on the transition it permitted"** — separate event or embedded object in the `transition` event? Test-strategy §1 says "passes + `override_used` annotation with blob SHA". Ledger schema tests need one answer. Similarly `stage` vs `transition` event types are both listed with no distinction (is `stage` the board-sync record?). **Fix:** decide both in the schema table (finding 2).

12. **[prd FR-3 vs architecture §Dispatch package] Section count disagrees (5 vs 6) and no tool owns package assembly.** PRD lists "role instruction, pinned inputs, expected outputs, stop rules, resume preamble" (5); architecture adds Header (6); test-strategy §4 asserts "all six sections". Worse: architecture says generation is "by the prep tools (`plan_prep`, `dispatch_prep`, `build_handoff`, `make_context_bundle`)" — four tools with overlapping-sounding outputs, none named "the package generator" that FR-3's acceptance invokes; `make_context_bundle` merely "feeds dispatch packages". Who writes Header, Stop rules, and Resume preamble into the final file? **Fix:** name one assembler (e.g. `make_package.py` composing bundle + role instruction + stop rules + preamble) and align PRD to six sections.

13. **[all docs] Story artifact layout is undefined, yet "expected outputs — exact artifact paths" and parity tests depend on it.** Architecture's diagram shows `stories/` "(specs, plans, evidence)"; test-strategy says drill evidence "lands in `stories/<id>/`". No doc names the files inside a story dir (spec.md? plan.md? test-plan.md? handoff.md? state.md? evidence/?). The dispatch package's Expected-outputs section, the parity "identical paths" assertion, and `render_state.py <story>` all need this frozen. (Old onboarding README's `stories/{id}/state.md` is the only concrete hint.) **Fix:** add a story-directory layout table to architecture.

14. **[architecture §Control plane] Gate catalog is not enumerated, and names conflict.** Tools table lists "plan gate incl. contract-seam + coverage checks; pre-review gate; digest gate" — "contract-seam" and "digest gate" are reference-implementation terms defined nowhere in the bundle (scope leak + undefined). Test-strategy's command `pre_review_gate.py plan <story-dir>` implies the *plan gate* is a subcommand of `pre_review_gate.py`, contradicting the separate-gates reading. Architecture open item admits gate naming (G12/G13/G14 vs slugs) is unresolved. **Fix:** publish the v0.1 gate catalog: gate id/slug → script + invocation → failure message contract → which transitions require it; define or drop "contract-seam"/"digest".

15. **[readiness C-11 vs everywhere] `KICKOFF.md` + `PREFLIGHT.md` are orphan requirements.** C-11 requires both present and "preflight re-runs", but neither PRD nor architecture mentions KICKOFF.md at all, and the new architecture §Onboarding doesn't say `onboard.sh` writes PREFLIGHT.md (only the *legacy* onboard.sh does, with nondeterministic content: pass/fail counts, target path). Who generates them, with what content, and is PREFLIGHT.md a render (byte-for-byte rules?) or a report? **Fix:** either drop C-11 or specify both files in architecture §Onboarding (recommend: PREFLIGHT.md = verify-mode output report, explicitly exempt from render determinism; KICKOFF.md = installed template).

16. **[readiness C-6 + architecture §Integrations] Board Stage field mechanics undefined.** C-6 requires "the `Stage` field (and derived group/status fields)" — "derived group/status fields" are never defined. `sync_board.py` writes "Stage … explicit, never inferred" — presumably Stage options must equal the 16/17 state names, but nothing says who creates the field/options (onboard.sh? manual?), what happens when a state name has no matching option, or what gh scope/GraphQL failure looks like (ties to finding 9). **Fix:** specify Stage option set = state names, creation responsibility (onboard install step or documented manual remedy in the registry), and sync failure behavior (fail-closed refusal naming the missing option).

17. **[prd FR-12 + architecture] Merge-gate mechanics and LIVE_PROVEN are underspecified; TOCTOU risk.** FR-12: controller "verifies tested SHA == head SHA" — head of the PR at check time; if commits land after MERGE_ELIGIBLE, is eligibility revoked and by what mechanism (a check at MERGED transition? re-run rule?)? Then "human merges → live-proven": who detects the merge (polling `gh pr view`? evidence = merge commit SHA?), and what does LIVE_PROVEN *mean* for a target with no deployment (benchmark-app)? No evidence key is defined for either transition (instance of finding 2, called out because D-1 must pass through both). **Fix:** define MERGED evidence (merge commit SHA recorded via gh) and make LIVE_PROVEN's evidence target-configurable with an explicit "no deployment — attested" path (null+reason) for v0.1.

18. **[prd NFR-3 vs onboarding/onboard.sh (to be ported)] macOS claim vs bash-4-only script.** The shipped `onboard.sh` uses `declare -A` (bash ≥ 4) and GNU-ish `find` usage; macOS ships bash 3.2. Architecture says onboarding is "`onboarding/`, extended" — i.e., this script is the port base. NFR-3 promises macOS. **Fix:** require bash ≥ 4 detection with a clear refusal naming the remedy (Homebrew bash), or rewrite POSIX/parallel-array style; state the decision in architecture §Onboarding.

19. **[architecture §Onboarding + prd FR-11] "Never overwrites" idempotent install has no upgrade/drift story.** Registry version is "recorded in the target", but when the kit version advances, installed `factory/tools/*` are never overwritten — targets silently drift from the kit, and verify would PASS a stale, buggy toolset (version recorded ≠ version enforced). **Fix:** define v0.1 behavior: verify reports kit-version vs registry-version mismatch as FAIL (or WARN — pick one) and onboard gains an explicit `--upgrade` path or documented manual remedy.

20. **[test-strategy D-1 + prd FR-2, success criteria] Several acceptance criteria are judgment calls dressed as tests.** "Pass = the runbook needed no outside knowledge", "without asking project-specific questions", "validated by a cold read from a fresh clone", FR-12 "any other question to a human during a run is a process defect and is logged as such" — none has an observable, mechanical pass/fail. Who is the cold reader (a person who has never seen the kit? another agent?), what counts as "a question", and where/how is a "process defect" logged (ledger event type? which)? **Fix:** operationalize: cold-read = a fresh-context agent or uninstructed human given only the clone + runbook, success = completes D-1 with zero clarification requests, each request recorded as a `finding`/`human_gate` event with a defect flag; state this in test-strategy §Drills.

21. **[prd FR-5 + test-strategy §2] "Byte-for-byte" render determinism has no byte contract, and render inputs may include forge state.** Renders are checked "match the ledger byte-for-byte" — but if `DASHBOARD.md`/`PROVENANCE.md` include PR status, board Stage, or wall-clock regeneration timestamps, the check is unstable by construction. No doc pins: timestamp format (ISO-8601 UTC? epoch?), JSON key order in embedded data, sorting rules, line endings, or which inputs are legal (ledger-only vs ledger+git vs ledger+git+GitHub). **Fix:** freeze a render byte contract in architecture: renders derive from **ledger + git only** (no live forge reads), UTC ISO-8601 `YYYY-MM-DDTHH:MM:SSZ`, sorted keys, LF endings, no generation timestamp in output (or a deterministic content hash instead); state it as a NFR-2 clarification.

22. **[architecture §Control plane] `dispatch_prep.py`'s "hard-read gate block" and `plan_prep.py`'s "paste-ready block" are undefined reference-implementation terms.** Neither phrase is explained; their relationship to the dispatch-package schema (are they sections? separate artifacts? who consumes them?) is unstated. A builder would invent both. **Fix:** define each in one sentence with its output artifact path, or drop them from v0.1 scope.

23. **[prd FR-6] "Claim is required before the first active transition after BACKLOG" — ambiguous boundary.** Does BACKLOG→SPEC_FROZEN itself require a claim (literal reading: yes, it is the first active transition after BACKLOG), or only transitions after SPEC_FROZEN? Idea intake/spec freezing may legitimately happen pre-ownership. Also: does claim require a story branch/worktree to exist yet? **Fix:** name the exact first claim-gated transition in the transition table.

## Minor issues / polish

24. **[prd vs docs/context-bundle.md template] Convention deviations:** FR numbering is `FR-1…FR-12`, template requires `FR-X.X`; template requires 2–3 Given/When/Then scenarios per FR — FR-1, FR-8, FR-11 carry 1–2 checklist items (PRD's own preamble legitimizes checklist-only for mechanical requirements, but FR-8's interface constraint is behavioral); template's 4th doc is `ui-design.md` — the bundle substitutes `target-repo-readiness.md`. The UI-doc absence itself is a **correct** scope call (surfaces are generated markdown + GitHub; architecture §Out-of-scope states it explicitly) — no objection. But note the knock-on: legacy `onboard.sh` posture detection counts `prd/architecture/ui-design/test-strategy` docs; a kit-onboarded repo's bundle will never match that pattern. **Fix:** one line in architecture acknowledging the template deviation + update posture detection when onboard.sh is extended.

25. **[architecture §Data model] Dispatch ID `<story>-<role>-<attempt>-<unix>`:** attempt numbering authority (who assigns attempt N+1 — controller at pre-spawn? after which failure events?) and `unix` units (seconds, UTC) unstated. "Stable IDs" for events generally: format never given. **Fix:** one line each in the schema table.

26. **[test-strategy §Test Pyramid] "~70% / ~20% / ~10%" shares are untestable** (share of what — test count, runtime?) and add no constraint. Harmless; recommend labeling as indicative.

27. **[test-strategy D-1] "human adapter driving at least the control plane"** — garbled: the control plane is explicitly adapter-free (FR-4, "No AI is required for any control-plane step"). Presumably means "human operator drives, using the human adapter for role work". **Fix:** reword.

28. **[prd FR-1 vs architecture §Kit structure] "no process rule exists only in an agent runtime" vs "process skills (content → docs, pointers left behind)"** — if pointers *to* the skill system remain anywhere in the kit, FR-1's first checkbox ("no reference to any external skill system as a requirement") is at least confusingly worded. Presumably pointers remain in the *reference implementation's* skills. **Fix:** clarify direction of the pointer.

29. **[prd Out-of-Scope] "True concurrent story scheduling (prevented by the lock…)"** — the lock prevents two owners of *one* story; it does not prevent two stories running concurrently (readiness A-9's multiple worktrees implies it's allowed). The parenthetical conflates the two. **Fix:** reword to "concurrent execution of multiple stories is allowed but uncoordinated in v0.1; per-story serialization is enforced by the claim lock."

30. **[prd NFR-3 vs readiness C-1/C-2] "works … in locked-down networks where only the repo travels"** sits oddly with hard requirements on a GitHub remote and live gh auth. Presumably means the *process definition* travels in the repo; execution still needs GitHub. One clarifying sentence would prevent a mis-scoped story. (The genuinely locked-down path is the v0.2 `api-direct` adapter.)

31. **[readiness C-4/C-5 vs legacy onboard.sh] Label set and issue-form are not frozen.** C-4 says "idea/planning/…/done, needs-human"; the legacy script creates `factory:planning…factory:done`, `needs-human` and **no** `idea` label; C-5 additionally requires an issue form template that nothing in the bundle defines (filename, fields). **Fix:** publish the exact label list (with colors, matching legacy convention) and the issue-form filename in architecture §Onboarding.

32. **[readiness C-13] Verify "executed once by verify with the project's health check"** — running a project's docker-compose test environment inside a CI-gateable verify is heavy and will make verify slow/flaky in CI; also undefined what "health check" means for arbitrary targets. **Fix:** allow C-13 to PASS via recorded manual attest (the doc's own attest mechanism) or a cached last-run, and mark full execution as drill-only.

33. **[architecture §Configuration] "identity (owner names, agent identity)"** — how identity is consumed (claim `owner`/`host`/`session` fields? git author? gh actor?) is unstated; likewise branch slug generation rules for `story/<id>-<slug>`. One line each.

34. **[test-strategy §Test Data] Two fixture trees (`factory/gates/fixtures/` and `tests/fixtures/`)** while the discovery command only scans `factory/tools` — where do `tests/fixtures` consumers live, and does `tests/` ship to target repos? Minor layout ambiguity (ties to finding 4).

## Decisions needed from the product owner

Each with recommended answer:

- **D1 — Ledger push model (finding 1).** Where does `events.jsonl` live and how do ledger commits pass branch protection? **Recommend:** ledger on `main`; branch protection configured with a bypass for ledger-only commits by the operator role (documented in C-3's remedy text); claim writes use fetch→append→push retry with post-rebase uniqueness re-validation so duplicates never land.
- **D2 — Config format & schema (findings 3, architecture open item).** **Recommend:** TOML (`config.toml`, `tomllib`, Python ≥ 3.11 pinned in Dependencies), keys frozen in architecture: `repo`, `default_branch`, `project_id`, `identity.*`, `adapters.*`, `kit_version`.
- **D3 — Self-containment extraction (finding 2).** Who writes the transition/evidence table, event schemas, and role catalog into architecture before decomposition — and confirm builders get zero access to the reference implementation. **Recommend:** doc author extracts now; treat architecture as un-finishable for grill pass until the tables exist.
- **D4 — State machine wording (finding 7, PRD open item "port as-is vs trim").** **Recommend:** port as-is, restated as "16 pipeline states + BLOCKED"; no trimming in v0.1 (trimming re-opens the evidence table).
- **D5 — Gate catalog naming (architecture open item: G12/G13/G14 vs slugs).** **Recommend:** descriptive slugs (`plan-gate`, `pre-review-gate`, …) — numeric IDs are meaningless without the reference doc and violate the genericization port rule.
- **D6 — `record_usage.py` manual entry path (architecture open item).** **Recommend:** keep a manual CLI (`--tokens N | --null-reason "…"`); human mode cannot close dispatch lifecycles (NFR-6, FR-10) without it.
- **D7 — Dispatch-package section count & generator ownership (finding 12, PRD open item "exact section schema").** **Recommend:** six sections (Header, Role instruction, Pinned inputs, Expected outputs, Stop rules, Resume preamble); one assembler tool owns the file, prep tools feed it.
- **D8 — Adapter manifest format (finding 5).** **Recommend:** `adapters/<name>/adapter.json` (machine-read by controller/router/verify) + README.md (human prose); FR-8's constraint test validates the manifest schema.
- **D9 — Verify check registry format (PRD open item; readiness §Notes manual-attest).** **Recommend:** JSON registry (`onboarding/checks/*.json`: id, category, script, remedy, attest_allowed) with adapter checks under `adapters/*/checks/`; attest records written as ledger events or a committed `factory/attestations.md` (pick: recommend ledger `human_gate` events).
- **D10 — C-11 KICKOFF.md: keep or drop (finding 15).** **Recommend:** keep PREFLIGHT.md (verify output, non-deterministic report, render-exempt), drop KICKOFF.md unless the runbook story actually needs a kickoff entry doc — nothing else in the bundle references it.
- **D11 — Render determinism byte contract & legal inputs (finding 21).** **Recommend:** ledger+git only (no live forge reads in renders), UTC ISO-8601, sorted keys, LF, no wall-clock in output.
- **D12 — Live parity in v0.1 (finding 6).** **Recommend:** add a hermes-adapter leg to D-1 on the dress-rehearsal story (it is already a success criterion — make the drill match it), with path/shape contract as the diff.
