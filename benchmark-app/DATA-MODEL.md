# Data Model

## Overview
This repository uses a very small persistence model centered on file metadata. It is not a rich domain model; it stores a record of each uploaded file and the location of the file payload in external blob storage.

### Persistence strategy
- Primary database: PostgreSQL.
- Storage system for the file body: Azure Blob Storage-compatible storage via Azurite in local development.
- Data access layer: Entity Framework Core with the Npgsql provider.
- Schema management: ORM-generated schema at startup using `Database.EnsureCreatedAsync()` rather than explicit migrations or SQL scripts.

### How data is persisted
- Metadata is stored in PostgreSQL through `UploadDbContext`.
- Binary file content is stored in blob storage; the database stores a reference to the blob location (`BlobName`).
- The application does not currently use a repository abstraction, a unit of work, or a separate service layer for persistence.

## Entities / Domain Objects

### 1) UploadedFile
- **Class name / table name**: `UploadedFile` / `uploaded_files`
- **Purpose**: Represents a single upload receipt and its associated metadata.
- **Key fields**:
  - `Id` (`Guid`): unique identifier for the upload. Generated by the API and used as the primary key.
  - `OriginalFileName` (`string`, required): original filename supplied by the client. Stored as a required field with max length 512.
  - `ContentType` (`string`, required): MIME type supplied by the client, or defaulted to `application/octet-stream` if missing/blank. Stored as a required field with max length 255.
  - `SizeBytes` (`long`): file size in bytes, captured from the uploaded stream length.
  - `BlobName` (`string`, required): path-like blob reference used by Azure Blob Storage. Stored as a required field with max length 1024.
  - `UploadedAtUtc` (`DateTimeOffset`): timestamp of the upload event in UTC.
- **Relationships**:
  - No explicit relationships to other entities in the current model.
  - The entity indirectly relates to blob storage via `BlobName`.
- **Key behaviors**:
  - It is a simple persistence entity; no methods or computed properties are defined.
  - The controller constructs it during upload handling and persists it to the database.

### 2) UploadResponse
- **Class name / transport shape**: `UploadResponse` (not persisted)
- **Purpose**: API response DTO used to return upload metadata to the client.
- **Key fields**:
  - `Id` (`Guid`)
  - `FileName` (`string`)
  - `ContentType` (`string`)
  - `SizeBytes` (`long`)
  - `UploadedAtUtc` (`DateTimeOffset`)
- **Relationships**:
  - No database relationship; it is a projection of the `UploadedFile` entity for HTTP responses.
- **Key behaviors**:
  - Immutable record type.

## Relationships
The current data model is effectively a single-entity model. There are no join tables, many-to-many relationships, inheritance hierarchies, or polymorphic relationships.

Plain-text relationship summary:
- `UploadedFile` -> external blob object via `BlobName`
- `UploadedFile` -> HTTP response DTO `UploadResponse` via projection

There are no pivot entities or discriminator columns in the current codebase.

## Key Data Flows

### Creation
1. The client selects a file in the web app and sends it to `POST /api/uploads`.
2. The controller validates the incoming file:
   - non-empty
   - under the 25 MB limit
3. The API creates a blob path using a generated `Guid` and the uploaded filename.
4. The file content is uploaded to blob storage.
5. A new `UploadedFile` entity is created with metadata from the request and the blob path.
6. The entity is added to `UploadDbContext` and saved to PostgreSQL.
7. If the database save fails, the blob is deleted as a compensating action.

### Retrieval
1. The API exposes `GET /api/uploads/{id}`.
2. The controller queries the database using EF Core and `AsNoTracking()`.
3. The entity is projected into `UploadResponse` for the HTTP response.
4. No additional query shaping, joins, filters, or pagination logic is present.

### State changes
There is no workflow state machine or lifecycle state for uploads in the current system. An upload is effectively treated as a single immutable record once created. The only meaningful state transition is:
- `not stored` -> `stored in blob + stored in DB`
- or, on failure, `blob uploaded but DB write failed` followed by attempted cleanup

## Storage Outside the Database

### Blob storage
- **Where**: Azure Blob Storage-compatible endpoint, locally emulated by Azurite.
- **How referenced**: The database stores the blob location in `BlobName`.
- **How created**: The API uses `BlobServiceClient` and `GetBlobContainerClient(...).GetBlobClient(blobName)`.
- **How used**: The actual file bytes are stored there; the database only tracks metadata.

### In-memory state
- The web app holds transient UI state for selected file, upload progress, receipt, and errors.
- This state is not persisted or shared across sessions.

### External data ownership
- The application does not read data from other databases or services in the current implementation.
- The only external system that owns the file payload is blob storage; the database stores only a reference to it.

## Constraints and Rules

### Required fields
The EF model enforces the following required fields:
- `OriginalFileName`
- `ContentType`
- `BlobName`
- `UploadedAtUtc`

### Length constraints
The EF model also enforces length limits:
- `OriginalFileName`: max 512
- `ContentType`: max 255
- `BlobName`: max 1024

### Validation rules enforced at the API layer
- File must be present and non-empty.
- File size must be at most 25 MB.
- If `ContentType` is missing or whitespace, the API defaults it to `application/octet-stream`.

### Data integrity behavior
- The upload operation is designed to prevent a metadata record from surviving if the database save fails after the blob has been uploaded.
- The controller attempts to delete the blob if the database write fails.

### Important limitation
- There is no database-level uniqueness or referential integrity beyond the primary key and required-field constraints.
- The current schema does not enforce uniqueness on file names, content types, or blob paths.
- The model is intentionally simple and benchmark-oriented rather than production-hardened.
